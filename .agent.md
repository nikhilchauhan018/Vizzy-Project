## 1. What this project is

**Vizzy** is a chat-driven web app that lets a user create a graphic novel / comic /
storyboard through conversation instead of a traditional editor, then exports the
finished pages as a video/slideshow.

**Core user flow:**
1. User sets up a **Style Bible** once (art style, color palette, tone, story notes/script).
2. Vizzy (the AI) asks clarifying questions and breaks the story into a **page/panel sequence**.
3. For each page: user describes the panel → Vizzy generates multiple image options →
   user picks one → user refines it conversationally → user approves → move to next page.
4. Once all pages are approved, they are **stitched into a slideshow/video** (ffmpeg,
   crossfade or Ken Burns pan/zoom, optional captions/narration).

**Non-negotiable product requirement:** image generation must NEVER be a blocking HTTP
call, must NEVER lose in-progress work if a provider goes down, and must fail over to a
backup provider mid-task without restarting from zero.

## 2. Tech stack (LOCKED — do not change without asking the human)

| Layer | Choice | Why |
|---|---|---|
| Backend framework | Django + Django REST Framework | Fast data modeling via ORM/admin for pages/versions/assets |
| Async job queue | Celery + Upstash Redis (broker + result backend, rediss:// TLS) | Decouples image gen latency from request/response cycle |
| Database | Neon (Serverless PostgreSQL via DATABASE_URL) | Relational integrity for story→page→version chains |
| Realtime updates to client | Django Channels (WebSockets) over Upstash Redis | Push "your images are ready" to chat UI without polling |
| Frontend | React + Tailwind CSS | Fast iteration on chat UI + image galleries |
| Reverse proxy / load balancer | Nginx (2+ app server instances behind it) | No single point of failure |
| File storage | Cloudinary (managed image and media storage) | Free-tier managed media storage; direct secure HTTPS delivery |
| LLM provider(s) | Gemini API (primary, free tier) → Groq → OpenRouter (fallbacks) | Free-tier friendly, swappable via provider abstraction |
| Image gen provider(s) | Pollinations.ai (primary, free/no-key) → Hugging Face Inference API (fallback) | Free-tier friendly, swappable via provider abstraction |
| Video assembly | ffmpeg (run inside a Celery worker) | Standard, scriptable, free |

See `docs/ARCHITECTURE.md`, `docs/API_PROVIDER_FAILOVER.md`,
`docs/LOAD_BALANCING_AND_RATE_LIMITING.md`, `docs/FOLDER_STRUCTURE.md`,
`docs/DATABASE_SCHEMA.md` for full detail on each of these.

## 3. Decisions Log (LOCKED unless marked otherwise)

- **LOCKED (2026-09-26)**: Infrastructure is Neon (Postgres), Upstash (Redis), Cloudinary (image/media storage) — all managed free-tier services, no self-hosted database/cache/storage anywhere, including local dev. Never reintroduce AWS S3, boto3, or a local postgres/redis docker-compose service.
- **LOCKED (2026-09-26)**: Django is the sole backend. Any frontend-side server (Express, etc.) exists ONLY to serve static assets and return mock fixture data during frontend-only development — it must never call an external AI provider directly or implement business logic. Delete mock handlers as real Django endpoints ship.
- **LOCKED (2026-09-25)**: Stack is Django + Celery + React/Tailwind — confirmed, not
  switching to Node/Express. Do not revisit this without the human explicitly asking.
- **LOCKED**: Every provider call (LLM or image) goes through an internal abstraction
  (`ProviderRouter`) — application code never calls Gemini/Pollinations/etc. directly.
  Both LLM and image routers are singleton instances in `apps/providers/instances.py` —
  import from there, never instantiate a second `ProviderRouter` elsewhere (this would
  split circuit-breaker state across instances and defeat the failover logic).
- **LOCKED**: Every multi-step job (scene extraction → prompt compile → image gen) is
  checkpointed to the database after each step, so a provider failure resumes from the
  last completed step, not from scratch.
- **LOCKED**: App servers are stateless. No session data in local memory — everything in
  Postgres/Redis — so any of the 2+ app servers can handle any request.
- **LOCKED**: We keep every generated `PanelVersion`, not just the selected one (user can
  revert via `parent_version` chain).
- **LOCKED (v2, 2026-09-25)**: `StyleBible`, `Character`, and `Environment` are three
  SEPARATE models, not one merged "style" blob — a character's face/uniform and a
  location's weather are different consistency axes and must be referenced independently.
  See docs/DATABASE_SCHEMA.md "Key design notes".
- **LOCKED (v2)**: The LLM never generates an image prompt directly. It only fills in
  structured `Panel.scene_json`. A separate, deterministic (non-LLM) Prompt Builder
  (`apps/pages/services/prompt_compiler.py`) merges scene_json + the three bibles into
  the final prompt text. This keeps every generation inspectable/debuggable.
- **LOCKED (v2)**: `Page` and `Panel` are separate models — a page can hold 1 panel
  (cinematic mode), N panels (comic mode), or act as a storyboard frame. Never assume
  one page = one image anywhere in the code.
- **LOCKED (v2)**: Speech bubbles/captions (`apps/composition/models.py:TextElement`)
  are a canvas overlay layer, edited directly by the user (react-konva on the frontend).
  They are NEVER passed into the image generation prompt. Do not add dialogue text to
  `compile_prompt()` — this is intentional, not an oversight.
- OPEN QUESTION: Do we need per-story LoRA fine-tuning for character consistency, or is
  reference-image conditioning (img2img/IP-Adapter-style, via Character.reference_image_url
  and Environment.reference_image_url) enough? → Decide after Phase 3 testing (see
  progress tracker).
- **LOCKED (2026-09-25)**: Provider chains expanded to 5 LLM providers (Gemini, Groq,
  Cohere, Mistral, OpenRouter) and 3 image providers (Pollinations, Stable Horde,
  Hugging Face) specifically to stretch combined free-tier quota further. Adding another
  free provider later is a config + one adapter file — do this again if quota still runs
  out in practice.
- **LOCKED**: Every provider call checks a Redis rate budget (`rate_budget.py`) BEFORE
  attempting the call, in addition to the circuit breaker which reacts AFTER failures.
  Do not remove the budget check thinking the circuit breaker alone is sufficient — the
  budget check avoids wasted calls the breaker would only catch after the fact.
- **LOCKED**: Per-user concurrency is capped at 2 simultaneous `GenerationJob`s
  (`apps/jobs/services/concurrency_guard.py`), enforced via Redis so it's correct across
  every app server and worker. Wired into `tasks.py`; **NOT yet wired into the
  job-creation API view**, because that view doesn't exist yet (see task 9 below) — do
  this when building it, do not skip it.
